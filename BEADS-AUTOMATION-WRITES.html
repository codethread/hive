Automation writes after the system-bead simplification

Workshop evidence 24 October 2026 Proposed policy, current code

With system beads simplified to a title and JSON description, the remaining field-policy questions are concentrated in agent-visible workflow beads. Busy Bee currently puts results in stage notes, temporary settlement state in run notes, and machine-readable outcomes in close reasons. It also generates acceptance checklists inside descriptions.

The simplification applied here

System beads: title, status and labels remain valid; the content payload belongs in one JSON document occupying the entire description. Content payloads currently stored in design, notes, comments or close reason are technical debt to migrate. It does not determine the desired field policy. This is the working policy for this comparison; no code, live records or tracker configuration have been changed.

The main map below covers Busy Bee, Bee and Colony's direct write paths. “Automation wrote it” and “it is a system bead” are different facts. The author of the content may also differ from the tool that stores it.

The boundary that makes this simpler

System records — migration bucket

Workflow system beads hold checkpoints. Spawn beads hold execution requests. Under the new direction their application payload belongs wholly inside JSON in description. Existing locks, observations and outcomes elsewhere are listed later as debt.

Agent-visible records — discussion bucket

Workflow runs, stages and grouping beads contain work. Response beads contain authored answers. These are not labelled system, even when automation creates them. Their field use is the main subject here.

“Agents do not look at system beads” means they are outside normal work selection. Diagnostic tools and authorized system operations still read them. The simplification concerns content fields: description, design, notes, comments and close reason. Title, status and searchable labels are explicitly retained. Native identity, assignment and typed links are shown separately; this discussion has not proposed removing them.

Walk through the scenarios

Each scenario separates the content's author from the mechanism that records it.

Start a workflow

  1. The caller supplies the request. The workflow definition renders the run title and description from its input. Busy Bee creates the run beneath existing ordinary work, initially in progress.
  2. The definition supplies stage instructions. Busy Bee creates stage/group descriptions from those instructions and adds completion and discovery guidance. Driver-handled stages and groups start in progress; Bee-dispatched stages start open.
  3. The default “do work” workflow adds its acceptance checklist to those instructions. Consequently the checklist lands in description, not native acceptance criteria. This is definition-authored content stored by Busy Bee.
  4. For a dispatched stage, Busy Bee copies the rendered brief into the spawn prompt. Bee captures that prompt in the system spawn bead's JSON description. This duplication already crosses the work/system boundary; moving all system payload into description does not itself remove it.
  5. Colony claims the task under the Bee's identity. Native claim updates assignment/status while preserving its human owner. The claim does not create a work summary.
A concrete policy mismatch

Giving generated stages meaningful acceptance criteria will require a native acceptance field in the definition-to-bead path. Enabling draft/acceptance gates alone does not supply that missing data.

Evidence: A, B, G and H in the source index.

Save a result and finish a stage

  1. The worker or driver supplies the selected outcome and data. Busy Bee validates the payload against the workflow schema and saves the original input in stage notes.
  2. Busy Bee closes the stage. Its close reason is a structured lifecycle fact; success uses a fixed explanation. The selected outcome and detailed result remain in notes, not in that explanation.
  3. The driver collects the result. Busy Bee reads and parses the entire notes field. It advances the workflow and updates the system checkpoint. Groups and the run close when the workflow reaches their completion conditions.
Small examples of the actual storage contracts

Illustrative values using the current formats, not a copy of a live record:

Stage notes:

{"choice":"next","data":{}}

Stage close_reason:

{"kind":"busybee-lifecycle","formatVersion":1,"scope":"visit","runId":"RUN_ID","outcome":"succeeded","reason":"Original worker result saved; visit completed."}

The first is the authored outcome payload. The second records the engine's lifecycle conclusion. Neither is automatically the complete authored answer.

Cancel or fail a run

The operator supplies an explanation. Busy Bee appends a Busy Bee settlement: JSON line to the run's existing notes, records the inspected inventory, and closes pending generated work bottom-up with lifecycle facts. It closes the run and restores the original notes when settlement succeeds. If settlement is interrupted, the marker can remain and blocks new admission until resolved.

Colony also releases owned unfinished claims: it clears the assignee and changes in-progress work to open, preserving the owner and respecting HITL reservations. Its execution observations and request outcome are written to the system spawn bead, already assigned to the migration bucket.

Evidence: C, D, E and H.

Publish the agent's complete answer

The agent authors the answer; Bee files it. Bee creates a separate, closed response bead with a JSON description containing the body, author, producing task, optional spawn-request provenance and superseded response IDs. A response is visible independently of whether the producing task was accepted or the execution succeeded.

A correction creates a new response that explicitly supersedes the prior current answer. The original remains available. This is enforced by the response publication protocol; it is not a claim that the underlying generic Beads fields are intrinsically immutable.

A useful existing separation

Response payload already lives in JSON description without being a system record. The remaining policy question is the division between a complete answer and the main task's concise durable notes. Copying every answer into notes would reintroduce duplication; retaining essential conclusions and linking the full answer is a candidate, not an adopted rule.

The publisher currently creates responses already closed without explicitly supplying acceptance criteria or a close reason. Draft-first and required-close-reason compatibility therefore needs a deliberate implementation decision and validation; this inspection does not establish how future YAML gates would treat that creation path.

A plausible later change is to place workflow result and coordination payloads in the system record's JSON, while leaving the agent-visible work bead with description, acceptance and durable notes. That is a migration candidate, not a selected architecture. In particular, today's native closure couples status and lifecycle evidence in one operation; a relocation must preserve the completion/recovery contract and avoid two competing sources of truth.

JSON can carry fields at arbitrary nesting points, but a single description is still one mutable value. Consolidating writers changes update coordination; it does not provide independent atomic writes for each nested property. Likewise, native comment attribution and timestamps must be represented explicitly if the new JSON record still needs them.

What this map deliberately distinguishes

Agent authorship

A worker supplies a workflow result and authors a full response. A caller supplies a request or failure acknowledgment. Automation may store that material without having composed it. A programmatic write is not proof of system-authored content.

Runtime authorship

Locks, checkpoint structure, lifecycle facts, observation timestamps, query labels and generated completion instructions come from code. They can be interleaved today with agent-visible work even when the destination is not a system bead.

Colony's private SQLite checkpoints and local receipt, finish-report and stdout/stderr files are also separate from Beads. They are not automatically bead notes, comments or conversation transcripts. The new system-body rule is not a verified claim that all runtime persistence already fits in Beads.

Manual conversation capture remains the agreed modest first pass: agents may selectively add useful conversation material as comments where appropriate. This source map does not imply an existing automated transcript-capture service.

What has and has not been done

The requested simplification is applied to this comparison and recorded in the workshop notes. The application, tracker configuration and existing beads are unchanged. This is evidence for the next policy decisions; it does not execute the migrations, establish purge safety across clones or settle the remaining response/summary distinction.
