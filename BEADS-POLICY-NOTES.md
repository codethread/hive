## Graph-read performance investigation

ct requested performance and completeness experiments for linked-record retrieval, including `br dep list`, `br dep tree`, `br graph`, BV robot graph and Hive UI hydration. The report is [Reading linked beads: graph performance and limits](BEADS-GRAPH-PERFORMANCE.html); raw measurements and repeatable scripts are saved as `BEADS-GRAPH-*` artifacts beside this note. All load fixtures are disposable; the shared tracker was not used as a load-test target.

- `br graph` follows readiness-affecting relationships, omitting related diaries and reply links. Dependency list/tree and BV graph included those links. Native graph also interprets parent-child edges in execution-order direction; it is not a raw typed topology export.
- `br dep list --direction both` supplies typed direct-neighbor summaries. Tree supports depth but omits edge types and may repeat the same bead along multiple paths; its `parent_id` is a traversal predecessor, not a parent-child assertion. Deep repeat occurrences can also carry `truncated`.
- With 5,000 thin records, BV JSONL full graph took about 46 ms median; a 100-record full native show took about 3.7 s. With 1,000 records and 40.7 MB of bodies/notes/comments, BV graph stayed around 63 ms while show of 100 records took about 6 s. These are three-sample, locally warmed-storage observations, not latency guarantees or equivalent-work microbenchmarks.
- Dense links amplified tree output: 100 records and 4,950 edges generated 9,046 occurrences / 1.26 MB at depth ten. Diamond and cycle cases terminated with repeat markers. Depth one still includes every direct neighbor, so it cannot bound a broad star.
- Rooted native graph of a 1,000-node blocking chain timed out at 12 seconds in all three samples; its all-graph path and BV completed in roughly 23–31 ms. Treat this as a focused endpoint investigation, not evidence that every graph read is slow.
- The actual Hive UI topology/hierarchy helpers read the exported BV graph, select parent-child families and fetch native summary fields in batches of 500, with freshness checks before and after. They took approximately 124 ms for a 1,000-node parent-child family and 824 ms for 5,000; browser rendering and full board decoration were excluded. Related diaries are not traversed by that hierarchy. Detail relations are capped at 50 per direction after the full native read, with totals retained.
- A newly linked but unexported diary appeared in native dependency reads and BV SQLite, but not BV's older JSONL input. BV reported the selected file as loaded/not stale; native sync diagnostics exposed dirty state and coverage drift. Preserve Hive UI's surrounding freshness checks. No cross-machine sync behavior was tested here.

Conclusion for the workshop: linked diary/response records are plausible at these tested scales if tools discover topology first and selectively hydrate content. A frictionless attachment reader needs typed links, width/byte budgets, clear continuation and freshness. These findings do not authorize performance fixes or a new retention policy.

## Agreed policy

1. Create beads in `draft`.
2. Require acceptance criteria before a bead leaves `draft`.
3. Require all acceptance criteria to be completed before a bead moves to `closed`. Agents verify the work before ticking the corresponding items.
4. Use `description` for the task description: its problem, intended outcome, scope and context.
5. Put acceptance criteria in the dedicated `acceptance_criteria` field, normally as concrete, verifiable Markdown checklist items. Do not put or duplicate the acceptance checklist in `description`.
6. Do not use the `prerequisites` field. Represent prerequisite work as separate task beads with explicit blocking dependencies. For example, an implementation task depends on a separate test-setup task. This keeps each piece independently understandable, verifiable and assignable to an agent. A parent-child link groups work; it does not replace the blocking dependency.
7. Require a `close_reason` when closing a bead, enforced through the YAML closure policy. No additional minimum length or pattern has been chosen.
8. Do not use the native reported-gate protocol (`br gate report` and the `workflow.gates` requirements that consume those results). Its evidence does not travel through JSONL across machines. Set this feature aside for this policy; this decision does not remove the agreed acceptance-criteria or close-reason checks.
9. As a first pass, agents may manually capture useful parts of the user-agent conversation as comments on the relevant bead when they judge it appropriate. This is selective and discretionary, not a requirement to transcribe every conversation. More systematic capture and automation can be considered later.

ct's direction: “description for description, and acceptance criteria for acceptance criteria. No merging the two.” Scope clarification: “exactly the same policy between system driven beads and agent driven beads”; investigate and correct incompatible automation after defining the policy.

Labels: retain the existing [label policy](docs/beads-labels.md); ct considers this area already covered. No label-policy change has been requested. Labels support classification, filtering and visibility, and some have defined behavioral consumers: for example, Bee refuses autonomous execution of `hitl` tasks. The existing policy defines permitted vocabulary, scope and stewardship.

Relationships: the existing [task lifecycle](AGENTS.md#task-lifecycle) already distinguishes parent links for scope grouping from blocking dependencies for execution order, and requires completed children before parent completion. The [native relationship reference](docs/beads-meta.md#readiness-and-the-graph) distinguishes blocking from non-blocking types. No redesign has been requested; the agreed no-`prerequisites` rule builds on the existing use of explicit blocking dependencies. Parent-child links also participate in native readiness semantics, so they are not merely visual grouping.

## Native behavior established so far

- `description` is the native name of the body field. `design`, `acceptance_criteria`, `prerequisites`, `notes`, `agent_context` and `close_reason` are separate fields. Comments are separate entries with an author and timestamp; labels and typed relationships are separate collections.
- Description, design and notes share mutable text storage and bead-level metadata; they have no per-field author or timestamp. Separate native audit events are not per-passage metadata. `br update` replaces any of the three; only notes has `--append-notes`. Description also has direct create/file-input flags; design and notes use subsequent updates. Append behavior was checked in the installed CLI help and `src/cli/commands/update.rs` at the installed revision.
- Transition policy can require nonempty acceptance criteria before a specified status change, and can require nonempty criteria with no recognized unchecked boxes before another transition.
- These checks do not validate Markdown generally, require an actual checklist, assess the quality of the criteria or prove that the work satisfies them. A nonempty paragraph can pass the native completion check because it has no recognized unchecked boxes. Agents retain responsibility for meaningful criteria and verification.
- The transition-specific acceptance rule uses the dedicated field. A separate closure gate also scans descriptions, design and notes for acceptance checklists. The later configuration plan must account for that distinction to implement the agreed separation accurately.
- Native policy can require a completed prerequisite checklist, but the installed policy schema has no built-in field prohibition setting. The decision to leave `prerequisites` unused will be expressed in guidance and respected by automation; do not add a `prerequisites_complete` requirement.
- Native closure policy can require a close reason. A disposable-tracker experiment confirmed that terminal `br show` displays it in parentheses after the closed date, above the description. JSON exposes it as `close_reason`, alongside `closed_at` and `status`. Closing with a reason leaves the description and acceptance criteria separate and does not itself add a comment.
- Labels have native syntax, length and count validation. YAML can condition a transition gate on a label; it does not provide an approved-label vocabulary or label-steward authorization. A gate pass is explicitly reported with `br gate report`, not inferred from review prose.

| Relationship tested | Observed behavior | Candidate meaning here |
| --- | --- | --- |

## JSONL pruning and tombstone experiment

ct asked whether deleting a linked diary actually shrinks JSONL without leaving broken relationships, then proposed tombstoning first so other databases receive the deletion before physical purging. This remains a candidate cleanup sequence, not an approved maintenance procedure. [Experiment results and command receipts](BEADS-JSONL-PRUNING-EXPERIMENT.json) record native-generated snapshots and disposable receivers. No JSONL records were manually edited and no shared tracker was changed.

Two fixtures tested opposite directions of a `related` edge between a task and a diary containing eight comments. The task already held the durable conclusion in notes. Both produced the same local size results:

| State | JSONL bytes | Bead records | Diary comments | Relationship edges |
| --- | ---: | ---: | ---: | ---: |
| Before deletion | 4,614 | 2 | 8 | 1 |
| Ordinary deletion / tombstone | 4,534 | 2 | 8 | 0 |
| Hard deletion | 477 | 1 | 0 | 0 |

Native deletion removed the link in either direction, including when it was stored on the surviving task's exported record. Hard deletion removed the diary's entire JSONL record. No dangling edges remained. With automatic export enabled in these fixtures, the file changed immediately during deletion; a subsequent explicit flush had the same size. A fresh database imported the 477-byte snapshot cleanly, with the main task and its notes unchanged and the diary absent. Ordinary deletion retained the diary's content and comments as a tombstone, so it did not provide the intended storage reduction.

An existing database that had imported the original snapshot behaved differently: importing the hard-pruned snapshot with `sync --import-only` retained its old, open diary. Absence from an incoming file is not itself a deletion instruction for ordinary import.

A native three-way merge using the original shared snapshot as an explicit base recognized the incoming deletion, reporting one deleted issue and no conflicts.
