Reading linked beads: graph performance and limits

Measured on disposable trackers 24 October 2026 br 0.7.6 · BV 0.25.2

Using linked diary and response beads looks practical at the tested sizes, provided discovery stays separate from full-record hydration. The biggest risks are choosing an API that omits the links, expanding a wide or dense neighborhood without a result budget, reading every diary body, and confusing an exported snapshot with the current database.

The names conceal a significant difference

br graph is a readiness/dependency view. It omitted related and replies-to edges in the fixture. br dep list, br dep tree and bv --robot-graph could find those links. They are not interchangeable graph readers.

The automation write map has also been corrected: title, status and labels remain valid for system beads. The JSON-description simplification concerns content fields, including notes, design, comments and close reason.

The mixed fixture checked meaning, not just speed

Twelve records included a task, child, related diaries in both edge directions, mail/reply links, a closed reply, a blocking task, deferred/draft records, a system record, a tombstone and a disconnected task.

  • Direct dependency list found all nine incident links, including the tombstone edge.
  • Dependency tree found eleven reachable IDs, including the closed reply, tombstone and system record; it omitted relationship types.
  • Native graph from the task returned only the task and its blocking dependent. Whole native graph showed two readiness edges and represented the parent-child relationship in execution-order direction.
  • BV full graph returned eleven non-tombstone records and nine typed edges. A depth-one view returned nine nodes and eight edges; the closed reply was two hops away and only appeared in the full traversal.

The graph commands do not inherit the ordinary-work exclusion convention automatically. This controlled system-record inspection was deliberate; normal work selection still uses Hive's prescribed filters/recipe.

Small answer does not imply a small read

In a 5,000-record tracker where the root has only ten links, BV's depth-one output shrank from about 546 KB to 3 KB. Time stayed about 41–42 ms. This bounds the answer, but does not make the operation equivalent to a local indexed edge lookup.

Depth does not bound width

A star of 5,000 records is entirely within one hop. BV depth one returned all 5,000 nodes, almost the same 820 KB as the full graph. A task acquiring thousands of diary/mail links still needs a result-count or pagination strategy.

Native graph's source batches the currently known traversal frontier. In a chain that frontier is narrow, so repeated database reads remain. That is a plausible contributor to the timeout, supported by code inspection; this report does not claim a profiler-proven root cause.

Dependency tree uses repeat for previously expanded occurrences. In the installed version those entries can also have truncated: true. Interpret the flags together: not every truncated entry means the configured depth alone hid a new branch.

What Hive UI actually hydrates

  1. Check the export. The ordinary-bead hierarchy reader resolves the selected JSONL file and checks native sync status.
  2. Read topology through BV. It loads the exported graph and validates node counts, unique IDs, endpoints and source diagnostics.
  3. Select a parent-child family. It excludes system/bee/merge-labelled nodes and tombstones, then follows only parent-child edges. Family mode follows parents and children; outline mode follows descendants.
  4. Hydrate native summaries in batches of 500 IDs. These fields omit descriptions, notes and comments. Missing list records can fall back to exact show reads.
  5. Check freshness again. Changes during hydration mark the result stale. The board data layer caches family results for a ten-second window and supports explicit refresh cutoffs.

A related diary is not part of this hierarchy today. It can appear in the detail inspector's non-parent dependency/dependent lists. Those return up to 50 relationships per direction, together with a total count. That cap is applied after the full native detail read; it does not cap the underlying relation-fetch cost.

Freshness can hide a newly linked diary

In a separate controlled fixture, I exported a task and then added one diary plus its related link to SQLite with automatic export disabled:

ReaderResult
Native dependency listFound the new diary edge immediately
BV with explicit SQLite inputTwo nodes, one edge
BV with the older explicit JSONL inputOne node, no edges; its own source report said loaded and not stale
Native sync statusOne dirty record, database newer, coverage drift; detectable by Hive UI's surrounding checks

The JSONL result accurately described its selected file; it did not establish that the file contained the latest database changes. For a live agent handoff, “no diary in this snapshot” must not become “there is no diary.” This experiment did not perform or validate cross-machine synchronization.

How the linked-diary approach should use these readers

The Bee already knows its task and active diary. Read those exact records as needed. Repeatedly rebuilding the full graph provides little value for an append or checkpoint. Keep critical task conclusions in the compact main record; put detailed working history behind its link.

Read the main task's description, acceptance and durable notes first. Discover direct attachments with a typed bidirectional dependency list, or use a freshness-checked topology index if one is already available. Fetch title/status/labels for the candidate attachments in a batch, then open the selected diary or response. Do not expand every related record's body just to learn what is attached.

Include closed records deliberately. BV can provide a typed historical topology from a known snapshot; native detail supplies the body of a selected response or diary. State the snapshot boundary and preserve tombstone semantics. A whole retained diary history should be an explicit expansion, not the default cost of opening an old task.

The tested data supports the linked-record direction, but the frictionless reader still needs a contract: direct attachment types, type/label classification, an explicit width/byte budget, continuation behavior and freshness. A general recursive “follow every link” command would mix containment, prerequisites, mail and history, and could expand far beyond the original task.

Concrete follow-up candidates

  • Do not use native graph for diary discovery. Its omission of related/reply edges is semantic behavior, not a performance bug.
  • Keep the topology-then-projection pattern. Add a bounded attachment view alongside the UI's parent-child hierarchy, rather than turning diaries into children just to make them visible.
  • Investigate slow full hydration and rooted native graph separately. The 100-record show and long blocking-chain results are repeatable examples for focused performance work.
  • Retain source freshness checks. Root/depth filtering and BV source authority do not replace comparing the export with current native state.
  • Set limits by records and bytes as well as depth. Broad stars and dense graphs need meaningful continuation/completeness signals.

These are investigation conclusions and candidate implementation work. No performance fixes, runtime policy changes, tracker publication or repository code changes were made.

Method and retained evidence

Machine: Apple M4, macOS. CLI benchmark: three sequential fresh processes per command, deterministic mixed command order, first sample retained, no manual filesystem-cache flush. Fixture preparation naturally warmed storage. Native reads used explicit disposable databases with automatic import/export disabled; BV robot cache was disabled. Twelve seconds was the per-read timeout. Median is descriptive, not a percentile/service-level guarantee.

The main matrix uses ten synthetic fixtures, from 12 to 5,000 records. Supplementary fixtures compare blocking versus related edges and parent-child hydration. Fixtures were admitted through native JSONL import/export; the shared Hive tracker was never used as a load-test target. Setup/import cost is excluded. No million-node extrapolation, remote latency, peak-memory measurement, lock contention test or browser rendering benchmark is claimed.

The primary timings were collected sequentially. An initial UI-helper run overlapped a supplementary test; that UI run was discarded and replaced with the sequential samples shown here. The supplementary rooted-chain probes briefly overlapped that initial UI check. All three timed out; an additional isolated confirmation also exceeded the same 12-second limit.
